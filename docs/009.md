# Validação, limitações e melhorias futuras

Este documento registra como validar o projeto e quais pontos ainda precisam de evolução. Ele não substitui o [manual de uso](./MANUAL.md).

## Validação técnica rápida

Antes de uma apresentação ou entrega, valide:

| Área | O que conferir |
| --- | --- |
| Dependências | `npm install` ou `npm ci` executado em `ponto-escolar` e `gov.br-fake`. |
| Banco | MySQL ativo e schema aplicado. |
| Ambiente | `.env` criado nos dois projetos com variáveis coerentes. |
| Gov.br fake | Simulador iniciado e acessível. |
| Admin | Login administrativo redirecionando pelo fluxo Gov.br/OIDC. |
| Funcionário | Cadastro, login e registro de ponto funcionando. |
| Relatórios | Dashboard e relatório diário exibindo dados do banco. |

## Comandos úteis

No `ponto-escolar`:

```bash
npm run mvc:check
npm test
```

No `gov.br-fake`:

```bash
npm run check
npm test
```

> Observação: os scripts `npm test` existem nos `package.json`, mas dependem de arquivos em `test/*.test.js`. Caso esses arquivos não existam no projeto, o comando não valida uma suíte real da aplicação.

## Validação manual essencial

1. Iniciar MySQL.
2. Iniciar `gov.br-fake`.
3. Iniciar `ponto-escolar`.
4. Acessar `/admin/dashboard`.
5. Confirmar redirecionamento para `/auth/govbr/login`.
6. Concluir login no simulador.
7. Confirmar acesso ao dashboard.
8. Cadastrar funcionário.
9. Acessar a tela de ponto do funcionário.
10. Fazer login como funcionário.
11. Enviar localização válida.
12. Registrar as quatro batidas.
13. Confirmar bloqueio da quinta batida.
14. Conferir pontos no painel administrativo.

## Limitações atuais

| Limitação | Impacto |
| --- | --- |
| Gov.br oficial não configurado | O fluxo real depende de credenciais e endpoints oficiais. |
| Sessão admin em memória | Reiniciar o servidor derruba sessões; múltiplas instâncias exigem store externo. |
| `gov.br-fake` em memória | Códigos, tokens e sessões desaparecem ao reiniciar o simulador. |
| QR Code fixo | O QR Code funciona como atalho, não como token dinâmico. |
| Testes automatizados não confirmados | Existem scripts, mas a suíte própria pode não estar versionada. |
| Deploy não documentado como produção | O projeto é adequado para demonstração/local até que a infraestrutura seja definida. |

## Melhorias futuras

- Integrar com Gov.br oficial usando credenciais reais.
- Adicionar testes automatizados de services, middlewares e rotas principais.
- Criar testes para regras de concorrência no registro de ponto.
- Usar store persistente para `express-session`.
- Revisar a estratégia do QR Code caso seja necessário token dinâmico por unidade.
- Documentar deploy quando houver ambiente definido.
- Adicionar controle de múltiplas unidades escolares, se virar requisito.
- Melhorar observabilidade com logs estruturados persistentes.

## Itens que precisam ser mantidos

Mesmo em evoluções futuras, preserve:

- separação entre `ponto-escolar` e `gov.br-fake`;
- autorização admin dentro do `ponto-escolar`;
- validação de `state` e PKCE;
- segredo fora do código;
- proteção das rotas administrativas por sessão;
- validação de funcionário ativo antes do ponto;
- histórico de ponto no banco.
