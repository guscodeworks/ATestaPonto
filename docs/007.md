# Segurança

Este documento concentra as decisões de segurança do projeto. O fluxo Gov.br/OIDC está em [006.md](./006.md).

## Princípios

| Princípio | Aplicação no projeto |
| --- | --- |
| Não confiar no front-end | Permissão admin é validada no back-end. |
| Não expor segredo | Chaves, secrets e credenciais ficam em `.env`. |
| Não vazar token pela URL | Tokens devem circular em troca server-to-server ou cabeçalho adequado. |
| Separar identidade de permissão | Gov.br autentica; ATestaPonto autoriza. |
| Reduzir dados sensíveis | CPF é mascarado em respostas e logs quando possível. |

## Sessões administrativas

O painel administrativo depende de `req.session.admin`. A sessão é criada somente depois que:

1. o usuário autentica no provedor;
2. o callback é validado;
3. o sistema consulta `/userinfo`;
4. a identidade passa pela allowlist interna.

Em produção, o cookie de sessão usa `secure: true`. Em desenvolvimento, o projeto permite HTTP local.

## JWT de funcionário

O funcionário usa JWT separado do fluxo administrativo. Esse token:

- possui `role: "funcionario"`;
- expira conforme `FUNCIONARIO_JWT_EXPIRES_IN`;
- é validado pelo middleware antes de registrar ponto;
- não libera acesso ao dashboard.

## Senhas

Senhas de funcionários são armazenadas com bcrypt. A força do hash usa `BCRYPT_SALT_ROUNDS`, limitada pelo código entre 10 e 15.

`JWT_SECRET` e `SESSION_SECRET` precisam:

- ser diferentes;
- ter pelo menos 32 caracteres;
- não usar valores triviais;
- combinar tipos diferentes de caracteres.

## CORS e headers

O `ponto-escolar` usa:

- `helmet` para cabeçalhos de segurança;
- `cors` com allowlist em `CORS_ORIGIN`;
- bloqueio de `*` em produção;
- limite de tamanho para corpo da requisição.

## Rate limit

O projeto aplica limites em rotas sensíveis, como login, administração e registro de ponto. Isso reduz abuso por repetição automatizada.

## Localização

A validação de localização ajuda a reduzir marcação fora da área permitida da escola. Ela não substitui outras políticas institucionais, mas adiciona uma barreira técnica ao registro remoto.

## Simulador Gov.br

O `gov.br-fake` deve usar apenas dados fictícios. Ele não deve ser exposto como serviço oficial, não deve coletar dados reais e não deve receber credenciais reais.
